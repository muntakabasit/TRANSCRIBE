## 1. Design's key observation: the label is a trace of human attention

The label field is being used in a *human* way: names, partial references, topical reminders, work hints, remembered phrases, imperfect spellings, and sometimes whole future-facing ideas. A forced upfront folder/project choice would punish the behaviour that is currently working.

**Library should do the organisational work after capture** without rewriting source custody. Reading/encountering real captured content should dominate the screen; the exact human label should travel with it as secondary authored context. When content isn't retrievable, show the label with its **honest available source status**, not a fabricated excerpt or source thumbnail.

No generic coloured “PROJECT / VOICE / BRAND” chips on every record: they would present analytic guesses as facts, especially since the user's category groupings were NOT native record fields.

**Illustration note:** “Guy man voices” is a **real reported label example**, NOT verified to be a playable voice file or an actually present transcript in this Design pass. A mockup must show a clearly labelled source unavailable/undemonstrated state until actual record joins are inspected. Showing a fake speech excerpt next to this label would be a false source claim.

When multiple capture/job records truly refer to **the same verified source**, present one intelligible encounter when safe, keeping the underlying record and attempt identities recoverable; never deduplicate captures solely because their label strings resemble one another.

### Search behaviour

- Search should find the exact original label anywhere in a record as reliably as the contained transcript/media source (when indexed).
- Treat case, punctuation, whitespace and token-order equivalence as low-risk *search matching* helpers; keep source spelling unchanged.
- Spellings such as **Guyman / Guy man**, **Shadow taught / Shadow taut**, and **British voice / Voice British** may return one another **as clearly marked approximate/suggested results** when the source text provides no stronger match.
- Present precise matches first; then **“Possible matches”** with the original wording visibly preserved. Give an easy way to turn approximate matching off or refine it.
- Search and sorting must not promote a project identity, merge source records, or deliver anything to another app.
- Metadata, source ID, original locator, and job history remain inspectable but not the primary surface.

**Counterexample to guard:** A query for “Ofa Rick” must not silently include Ofa Jack records based on presumed project equivalence. Only actual human approved relationship or independently established context would support association.

## 3. Capture's useful minimal default (no new required classification)

**When user saves:** content/source custody first → optional free-text label. No mandatory title, category, project dropdown, pre-chosen worker or destination. Keep human-entered text through share-sheet dismissal or interruption. If a label is edited, the edit is on that same capture, not a second submission.

Any “Also work with…” suggestion must be **visibly distinct from the label field**, grounded in a currently recognised receiving project (otherwise don't suggest), optional, and cannot silently initiate a cross-project handoff. The human may still leave the field empty or save a full sentence.

Labels such as “News feed idea daily new tech discoveries things that matter to me” show why *maximum meaning* can be a complete thought rather than a short tag; input design must accept ordinary language without forcing an artificial naming convention.

## 4. Source-grounded discriminating review; no new code

Use an owner-approved set of actual records whose original access, label, transcript/media availability and privacy permit review:
1. **Variation:** Search `Guyman` and `Guy man`; demonstrate that six distinct source records remain six even when the search gathers close matches. Exact labels visible.
2. **Order:** Search `British voice`; `Voice British` returns as a related search result *only with correct grounded matching*, never with silently modified label.
3. **Spelling:** `Shadow taut` is visible as originally written even when `Shadow taught` is also found under explicitly approximate search.
4. **Project-looking label:** `Ofa Rick` retains its wording; the Library does **not** claim delivery, because reported destinations are all empty.
5. **Long thought:** the technology-discovery-feed label remains legible and searchable even if the original has a long full-sentence label.
6. **Source status:** compare one completed true transcript, one preserved link-only record, and one genuinely unavailable source. **No fake thumbnail, no duplicate reprocessing, no media disappearance from Library.**
7. **Retrieval:** exact reading/listening return survives switching context only where actual stored position exists; no manufactured “Continue”.
8. **Accessibility:** VoiceOver reads original label and true source state; Dynamic Type wraps long labels; high zoom/large touch targets, no truncation that hides distinguishing words.

**Rejection criteria:** User must not relearn their vocabulary, guess what a suggested grouping means, see fake capture previews, lose source location, or mistake “a project was mentioned” for “material was delivered.”

**Human judgement:** Is a formerly hard-to-find capture now recognisable and recoverable within the actual Library? Does the content—not bureaucracy—invite return?
